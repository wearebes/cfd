# Ubuntu 22.04 HPC operator handoff for Claude review

Date: 2026-07-13  
Status: implementation and Linux amd64 OpenMP smokes pass; the real Ubuntu
22.04/128-CPU host gates have not yet been executed.  
Execution model: one formal row at a time, OpenMP inside the row, no
MPI/Slurm/GPU/PyTorch.

## 1. Frozen experiment identity

The formal matrix contains exactly 180 rows:

| Benchmark | Resolutions | Methods | imax | Rows |
| --- | --- | --- | --- | ---: |
| `capwave` | 64, 128, 256, 512 | native + NN cell-offset | 0-5 | 48 |
| `rising_case1` | 64, 128, 256, 512 | native + NN cell-offset | 0-5 | 48 |
| `rising_case2` | 64, 128, 256, 512 | native + NN cell-offset | 0-5 | 48 |
| `stationary_bubble` | 64, 128, 256 | native + NN cell-offset | 0-5 | 36 |

There are 90 native and 90 NN rows. Stationary N512 is forbidden. Rising Case
2 is compiled with `CASE2=1`; Case 1 is not. Every NN branch uses the same
canonical cell-offset header and resolution-specific `baseline_<N>_hgradient`
weights.

## 8. Canary and capacity gate

```bash
python3 hpc/run_canaries.py \
  --matrix-id "$MATRIX_ID" \
  --cpus 128 \
  --policy hpc/config/thread_policy.json

jq . hpc/results/$MATRIX_ID/platform/capacity.json
jq -e '.status == "PASS" and .measured_openmp_scaling == true' \
  hpc/results/$MATRIX_ID/platform/capacity.json
```

The canary runs capwave, rising Case 1, rising Case 2 and stationary N64 NN
correctness smokes. It then measures stationary N64 at the supported subset of
1/16/32/64/128 threads. Raw canary outputs are deleted after the report.

Important: `capacity.json` reports recommended single-row and throughput
thread counts, but it does not rewrite `thread_policy.json`. The operator must
review the recommendation. If a different policy is accepted, copy the JSON
to a new repository-relative file, edit it, and use that exact file for both
submission and every resume. Its SHA-256 becomes part of result identity.

## 10. Start the formal matrix

Run in a persistent session. The first submission must not use `--resume`:

```bash
nohup bash hpc/submit_matrix.sh \
  --cpus 128 \
  --matrix-id "$MATRIX_ID" \
  --policy hpc/config/thread_policy.json \
  --max-active-rows 1 \
  > "hpc/${MATRIX_ID}.submit.log" 2>&1 &

echo $! > "hpc/${MATRIX_ID}.pid"
```

`submit_matrix.sh` reruns preflight and canaries, then performs:

```text
180-row dry-run
48 N64 formal rows
N64 integrity gate
132 remaining formal rows in deterministic longest-first order
180-row full integrity gate
final result package
```

Only one row runs at a time. Each row uses the OpenMP threads specified by the
accepted policy and is pinned with `taskset`.

## 12. Resume after interruption

First confirm no old runner is active. Reuse the same matrix ID, policy file,
CPU count and row concurrency:

```bash
bash hpc/submit_matrix.sh \
  --cpus 128 \
  --matrix-id "$MATRIX_ID" \
  --policy hpc/config/thread_policy.json \
  --max-active-rows 1 \
  --resume
```

Valid completed rows are rehashed and skipped. A missing file, changed hash,
wrong identity or stale staging directory causes a hard stop; resume never
overwrites or silently repairs it.

The thread policy is frozen at first submission: its SHA-256 is bound into every
row's `formal_identity`. Resuming with a different policy file makes every
already-completed row fail the identity check and hard-stops. If the canary
motivates a different policy, you must start a **new matrix ID** and rerun from
scratch under that policy; you cannot swap the policy into an in-progress
matrix.

An unclean host termination may leave
`hpc/work/.submit_<matrix_id>.lock`. Remove that lock only after independently
confirming that no submit, matrix or row process remains active. Retain failed
work directories for diagnosis.

```text
hpc/results/<matrix_id>/
  platform/
    preflight.json
    capacity.json
    provenance.lock.json
    thread_policy.json
    lscpu.txt
    numactl.txt
    memory.txt
    disk.txt
  capwave/N####/imax##/<method>/
  rising_case1/N####/imax##/<method>/
  rising_case2/N####/imax##/<method>/
  stationary_bubble/N####/imax##/<method>/<mode>/
  launcher_logs/
  scheduler_n64.json
  scheduler_remaining.json
  matrix_manifest.json
  matrix_status.csv
  matrix_timing.csv
  failure_ledger.csv
  SHA256SUMS
```

Each completed row contains copied sources/headers, primary output, launcher
logs and a manifest with formal identity, platform, toolchain (gcc version and
`qcc` SHA-256), OpenMP environment, CPU-list, file SHA-256, byte count and line
count.

Stationary rows carry one extra level: the generator emits results under an
inner `clsvof_native/` or `nn_cell_offset/` mode directory plus `summary.csv`
and `summary.json`, so the primary series lives at
`stationary_bubble/N####/imax##/<method>/<mode>/La-12000-<level>`. This nesting
is intentional (`summarize_smoke.py` iterates per-mode subdirectories); capwave
and rising rows remain flat. Row integrity is unaffected because the manifest
and `SHA256SUMS` record the actual layout.

## 15. Known review points for Claude

Claude should explicitly decide whether these are acceptable before formal
launch:

1. The actual implementation defaults to one active row, while the original
   plan discussed multi-row CPU-token scheduling. This is an intentional later
   user decision.
2. Canary recommendations are recorded but do not automatically rewrite the
   policy; operator acceptance is required.
3. The scaling canary uses stationary N64, not N256. It validates OpenMP
   behavior cheaply but is not a full N256 performance prediction.
4. Preflight records RAM and disk but currently does not enforce fixed numeric
   minimums, following the user's decision not to use a memory gate.
5. `--cpus 128` means visible logical CPUs. The topology report must be read to
   determine physical cores and SMT.
6. The official Ubuntu 22.04 Docker gate could not be run locally because all
   official registries/CDNs returned EOF or TLS errors. Linux amd64 GCC/OpenMP
   Case 1/2 smokes passed under Ubuntu 24.04; Ubuntu 22.04 remains a real-host
   gate.
7. The deployment manifest hashes every transferred file, but it does not
   claim that the current untracked implementation is represented by a Git
   commit. The per-file deployment manifest and provenance lock are the
   authoritative identities.
8. Current row and canary records contain wall time but do not record peak RSS.
   This follows the user's decision not to gate on memory, but it differs from
   the original plan's resource-reporting ambition.
9. The default policy uses at most 64 OpenMP threads for one row. With
   `--max-active-rows 1` on a 128-CPU host, up to half the CPU pool is therefore
   intentionally idle. Claude/operator must either accept this latency policy
   or create and lock a measured policy after the 64/128-thread canary.

## 17. Changes applied after the first Claude review

These are source-level changes included in the reviewed `v8` package. Any
future source change requires a new deployment package and, if provenance is
re-locked, a fresh `preflight`.

1. Stationary NN generator now passes the same explicit NN knobs as capwave and
   rising (`-DKAPPA_OFFSET_CLAMP_FACTOR=1.0 -DKAPPA_OFFSET_PROBE_INTERVAL=0` and
   `-I cases/_shared/nn_cell_curvature/src`). The values equal the header
   defaults, so results are numerically unchanged; this removes silent drift if
   the header defaults ever change.
2. Each formal row manifest now records a `toolchain` block (gcc version and
   `qcc` SHA-256) under `execution`. It is provenance only and is not part of
   `formal_identity`, so it does not affect resume validation.
3. The scaling canary now records observed OpenMP speedup relative to the
   1-thread baseline (`openmp_speedup_by_threads`, `openmp_best_speedup`,
   `openmp_speedup_observed`) in `capacity.json`. This is recorded for operator
   review and is intentionally NOT a hard gate: the scaling workload is the
   short stationary N64 smoke, where thread-spawn overhead makes strict
   monotonicity noisy. `measured_openmp_scaling` semantics are unchanged. A
   `openmp_best_speedup <= 1.0` should prompt the operator to investigate before
   trusting the policy.
4. `submit_matrix.sh` now gates on the 180-row dry-run inline (181 lines and a
   summary `row_count == 180`) instead of only generating the artifact.
5. `provenance.lock.json` now also pins the six case generators and
   `cases/capwave/src/make_single_resolution_case.py`, so `preflight_hpc.py`
   re-verifies the compile-affecting scripts on the target host, not just the
   science headers.
6. Documentation: the stationary result path in section 14 now shows the
   intentional inner `<mode>/` subdirectory; section 12 documents that the
   thread policy is frozen at first submission and a policy change requires a
   new matrix ID.
7. Submission now propagates the selected policy into preflight, both matrix
   verification phases and final result packaging. This prevents a custom
   thread policy from being executed under one identity and verified under the
   default identity.
8. Deployment export now rejects `.dSYM` directories and the local
   `basilisk/src/config.osx`; the package keeps source plus a relative
   `config -> config.gcc` link only.

Not changed (deliberately deferred): peak-RSS recording (known review point 8)
was not added. Correct per-row peak RSS needs to capture the `qcc`-compiled
simulation, which is a grandchild of the generator's shell, so a simple
`getrusage`/`/usr/bin/time` wrapper on the generator would under-report it. This
was left for a dedicated change rather than a partial, misleading measurement.
